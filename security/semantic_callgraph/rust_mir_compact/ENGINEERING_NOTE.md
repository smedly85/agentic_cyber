# One exact compact-storage candidate

This note precedes implementation. The original inclusion.py remains the pinned reference. The prior performance candidate and all its evidence are preserved.

The remaining dominant volume is hundreds of millions of Python tuple memberships and billions of repeated token transfers. This candidate replaces memberships with independently numbered tokens per token kind, represented in sparse 256-bit integer blocks. Immutable block vectors are shared between cells. Exact bitwise union replaces element-by-element union; a bounded cache keys every immutable operand, so eviction affects only cost. Generation checks suppress unchanged cell-to-cell transfers. No token is dropped, no object identity is merged, and no allocation/field abstraction changes.

The candidate retains the previously validated first-collapse absorption and field indexes, but removes per-cell append-only token histories and mutable decoded-kind indexes. Decoding is needed only at semantic queries and output boundaries. General operand snapshots remain snapshots. Empty reads still materialize cells. The reference full sweeps, active-function iteration, 256-sweep safeguard and finalizer remain unchanged. SCC compression or a new worklist is deliberately not needed for this storage candidate: avoiding reordering also preserves the reference's cap-bound behavior.

Validation compares all 108 existing immutable inputs, full internal cell state, scientific output and normalized graphs, then repeats the candidate cleanly. Any scientific difference stops this task. Only after equality passes will printenv, mktemp and sort run, each at the original 900-second budget with a diagnostic memory safety guard. If these do not demonstrate practical convergence, stop; do not initiate another optimization cycle. If they converge deterministically, freeze the exact candidate and operational policy additively before historical measurement with unchanged mappings, classifier and depth definitions.
